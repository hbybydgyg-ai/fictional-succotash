صدى العراق — الإصدار الظاهر داخل التطبيق 2.21 (المعرّف التقني الداخلي 1.6.47)
دليل النشر والتحقق
================================

ما الجديد في 2.21
----------------
1. إصلاح آمن لتنظيف بيانات التشغيل من خلال الخادم فقط، مع جلسة مدير وتحقق من Origin وتأكيد صريح. ينشئ نسخة استرجاع خاصة قبل الكتابة، ويستخدم تحديث Firebase متعدد المسارات ذرياً ثم يقرأ المسارات ويتحقق منها قبل إعلان النجاح.
2. التنظيف يشمل الحسابات والمستخدمين والطلبات والمدفوعات وسجلات الأرصدة والخصومات وطلبات الرصيد المجاني وعمليات إعادة التعبئة ومحادثات الدعم والإشعارات ومفاتيح API والبيانات التشغيلية المرتبطة. تبقى الخدمات والأقسام والأسعار وترتيب الكتالوج والمزودون وإعدادات الموقع محفوظة.
3. في حالة PERMISSION_DENIED أو فشل اتصال/قراءة Firebase، لا يمسح الخادم ملفات التشغيل المحلية ولا يعرض نجاحاً كاذباً. قد تُنشأ نسخة استرجاع قبل محاولة الكتابة؛ لا تشاركها لأنها تحتوي بيانات خاصة.
4. إضافة API محمي لفحص وإصلاح بيانات الأقسام/ترتيبها من صفوف الخدمات التي ما زالت موجودة في Firebase، مع الحفاظ على صفوف الخدمات والأسعار. لا ينشئ خدمات وهمية.
5. تحسين رسائل التنظيف والإصلاح في لوحة الإدارة؛ تبقى إضافة الأقسام وتعديلها وحذف قسم محدد في المسارات الحالية مع تحقق من الحفظ في Firebase.

ملاحظات مهمة حول البيانات
------------------------
- هذا الإصدار لا يكتب إلى قاعدة Firebase الإنتاجية أثناء الاختبار المحلي، ولا يعيد تلقائياً خدمات أو أسعاراً تم حذفها نهائياً.
- زر «تنظيف بيانات التشغيل» ليس «حذف الكتالوج». إذا أردت حذف الخدمات والأقسام، استخدم إدارة الكتالوج وزر الحذف المخصص بعد تأكيد النطاق.
- زر «فحص وإصلاح الأقسام والخدمات» يستطيع إعادة بناء بيانات الأقسام وترتيبها عندما تكون صفوف الخدمات ما زالت موجودة في Firebase. إذا كانت الخدمات نفسها مفقودة ولا توجد نسخة احتياطية، يجب استرجاع نسخة محفوظة أو جلب خدمات المزود ثم اختيار الخدمات المراد استيرادها يدوياً. لا يتم استيراد قائمة المزود كاملة تلقائياً.
- إذا استمر PERMISSION_DENIED، تحقق من `FIREBASE_DATABASE_URL` ومن أن `FIREBASE_SERVICE_ACCOUNT_JSON` أو `FIREBASE_SERVICE_ACCOUNT_BASE64` يشير إلى حساب خدمة للمشروع نفسه. لا تفتح Firebase Rules للقراءة والكتابة العامة لتجاوز الخطأ.

قاعدة Firebase Realtime Database هي المصدر الأساسي للخدمات والأقسام والأسعار. كل إضافة أو تعديل أو حذف في الكتالوج يجب تأكيده من Firebase قبل إظهار نجاح العملية. جلب المزود يعرض معاينة فقط؛ الحفظ لا يتم إلا بعد اختيار الخدمات والضغط على «رفع الخدمات المحددة».

ملفات التشغيل في جذر المشروع مباشرةً:
- server.js: خادم الموقع ومسارات API.
- index.html: الواجهة.
- package.json وrailway.json: تشغيل Railway.
- version.txt وBUILD_ID.txt: علامات الإصدار التي يقارنها /api/health.
- bundled-assets.json وapi-addon.js وfirebase-messaging-sw.js: ملفات يحتاجها التطبيق.
- admin-auth.json: يحتوي بصمة كلمة مرور الإدارة (scrypt) فقط؛ لا يحتوي كلمة المرور بالنص.
- config.json وdatabase.rules.json: إعدادات مساعدة؛ احتفظ بها.
- tests/: اختبارات محلية فقط؛ لا تُستخدم كملفات تشغيل للموقع.

حتى يظهر التحديث فعلاً:
1) فك ضغط ZIP على جهازك. لا ترفع ZIP نفسه إلى GitHub كأنه كود المشروع.
2) افتح مستودع GitHub المرتبط بخدمة Railway، واستبدل ملفات المصدر في جذر المستودع. يجب أن تكون server.js وindex.html وpackage.json وversion.txt مباشرة في الجذر.
3) أضف الملفات الجديدة المطلوبة من هذه الحزمة، بما فيها admin-auth.json وCHANGELOG_AR.md، وملفات الاختبارات مرتبة داخل مجلد tests/ وسجل التغييرات الحالي هو CHANGELOG_AR.md. لا تحذف بيانات الإنتاج أو ملفات التشغيل أو قاعدة Firebase.
4) تأكد في Railway من المستودع والفرع الصحيحين ومن أن Root Directory فارغ إذا كانت الملفات في جذر المستودع. ثم انتظر Deployment ناجحاً.
5) افتح https://رابط-موقعك/api/health?ts=رقم-جديد. يجب أن تكون version وuiVersion = 1.6.47، وأن تتطابق buildId وuiBuildId وversionFile وbuildFile، وأن تكون deploymentConsistent = true.
6) إذا بقي رقم أقدم في /api/health، تحقق من المستودع/الفرع/Root Directory/الخدمة، لا تفترض أنها مشكلة كاش فقط. إذا كانت health تعرض 1.6.47 والواجهة قديمة، افتح الموقع في تبويب خاص أو امسح كاش الموقع.

قبل النشر: احتفظ بنسخة احتياطية من بيانات Railway Volume الحالية، خصوصاً `services.json` و`category_meta.json` إن كانت موجودة. الحزمة المصدرية لا تحتوي بيانات كتالوج الإنتاج. لا تحذف الـ Volume أو ملفات البيانات.

إعدادات Railway المطلوبة:
- ADMIN_EMAIL: إذا ضُبط في Railway فإنه يستبدل بريد الإدارة الافتراضي الموجود في admin-auth.json؛ اتركه دون ضبط لاستخدام حساب الإدارة المضمّن.
- ADMIN_PASSWORD أو ADMIN_PASSWORD_HASH: متغيرات Railway إذا أردت تجاوز بيانات الإدارة المضمّنة. عند عدم ضبطهما، يستخدم المشروع بصمة scrypt مضمّنة لحساب الإدارة hsydgyg5@gmail.com؛ لا يوجد نص كلمة المرور داخل ملف الخادم أو الواجهة. تغيير كلمة المرور عبر استعادة البريد يحفظ بصمة جديدة ويعطّل بصمة الحزمة الاحتياطية.
- SESSION_SECRET: سر عشوائي ثابت وقوي (32 محرفاً أو أكثر). تغييره يبطل الجلسات الحالية.
- FIREBASE_DATABASE_URL وواحد من FIREBASE_SERVICE_ACCOUNT_JSON أو FIREBASE_SERVICE_ACCOUNT_BASE64. أبقِ محتوى حساب الخدمة داخل Variables ولا تضعه في GitHub أو ZIP.
- إعدادات API ومفتاح مزود الخدمات الصحيحين كما يحددهما المشروع؛ مزامنة الأسعار الحية لا يمكنها العمل دون اتصال مزود صالح.

الأسعار والربح:
نسبة 100% تعني إضافة مقدار يساوي تكلفة المزود فوقها (سعر البيع = ضعف التكلفة قبل الخصومات)، ولا تعني هامش ربح 100% من سعر البيع. تُرفض الطلبات إذا جعل الخصم الربح أقل من الحد المطلوب، أو تعذر التحقق من التكلفة الحية. افحص تكلفة المزود الفعلية والعملة ووحدة السعر قبل فتح الطلبات للمستخدمين.

اختبارات الحزمة:
npm test يشغّل اختبارات ترتيب الخدمات بالأسعار، ثم الفحوص الثابتة واختبارات API وآسياسيل عبر مزود وقاعدة اختبار محليين. لا تنفذ هذه الاختبارات تحويلات مالية حقيقية ولا تتصل بقاعدة Firebase الإنتاجية؛ تأكد من الإنتاج بحذر بعد التأكد من الإصدار.

أمان:
لا ترفع .env أو ملف حساب الخدمة أو مفاتيح API أو كلمات المرور إلى المستودع. لا تحوّل Firebase Rules إلى قراءة/كتابة عامة، ولا تحذف بيانات المستخدمين والطلبات والرصيد.

- الحد الأدنى في آسياسيل 1,000 د.ع. لا يُضاف الرصيد إلا بعد تأكيد نجاح التحويل من المزود.
- الاختبارات تستخدم مزود آسياسيل وهمياً وقاعدة اختبار محلية؛ لا تعتبر اختباراً لتحويل مالي حقيقي.


إضافات الإصدار 1.6.39: معالج آسياسيل من أربع خطوات، تنسيق مبالغ واضح بالأرقام 1000/2000/3000، تحسينات نموذج طلب الخدمة، وإصلاح جسر اتصال الإحصائيات. بعد نشر ملفات الحزمة كاملة افحص /api/health وتأكد أن version وuiVersion = 1.6.39 وأن deploymentConsistent = true. لم تُجرَ عملية تحويل آسياسيل حقيقية في الاختبارات.


إصلاح حماية مزامنة المزود في 1.6.39:
- لا تتسبب الخدمة الغائبة مؤقتاً من رد المزود في تعطيل خدمات الموقع أو إخفاء أقسامها.
- خطأ الشبكة أو الكتالوج الجزئي أو السعر الفارغ/الصفري المشبوه لا يكتب حالة unavailable إلى services.json.
- محاولة الطلب تظل مرفوضة مؤقتاً إذا تعذّر إثبات سعر المزود، لكن من دون تغيير حالة الخدمة الدائمة أو خصم رصيد.
- تُستعاد العلامات المؤقتة القديمة التي أنشأها الفحص الآلي غير الآمن فقط، مع احترام الحقول الصريحة لتعطيل الموقع.
- بعد النشر افحص /api/health وتأكد من version=1.6.39 وdeploymentConsistent=true.


إصلاح آسياسيل في الإصدار 1.6.44:
- إغلاق نافذة آسياسيل ينهي جلسة OTP العادية فوراً، ويمسح خطوة المتصفح؛ وعند الفتح التالي ينفّذ الموقع reset قبل فحص الحالة، لذلك يبدأ المستخدم من الخطوة الأولى ولا تعود الخطوة الرابعة القديمة.

- بعد النشر افحص /api/health وتأكد من version=1.6.44 وbuildId=SADA-1.6.44-RESTORE-DELETE-ALL-PROVIDER-CATEGORY-20261014 وdeploymentConsistent=true.
